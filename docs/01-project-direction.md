## 1. 한 문장 목표

**사용자와 함께한 경험을 기억하고, 현재 진행 중인 일과 맥락을 이어가며, 시간이 지날수록 적절한 방식으로 도움을 주는 개인 전용 AI 비서.**

장기적으로는 비서이자 친구처럼 편하게 대화하고, 모델이 바뀌어도 일관된 정체성을 유지하는 서비스를 지향한다. 초기 성공 기준은 AGI나 의식의 구현이 아니라 실제 생활에서의 연속성과 유용함이다.

대표적인 한 달 사용 경험:

> 한 달 뒤 접속해도 내가 누구인지, 무엇을 고민했고 무엇을 결정했으며 무엇이 남았는지 이해하고 대화를 이어간다.

## 2. 사용자와 기술 선택의 맥락

- 사용자는 Java/Spring 백엔드 개발 경험이 있고 React를 일부 배웠다. TypeScript는 Java만큼 익숙하지 않다.
- 별도 서버 운영 부담을 줄여 휴대폰에서 직접 사용해보고 싶다.
- 현재 구현 방향은 Next.js + TypeScript + Supabase + Vercel이다. AI SDK로 모델 공급자 연동을 추상화한다.
- TypeScript 학습을 프로젝트와 병행한다. 작은 기능의 코드 흐름을 이해하면서 확장한다.
- Java/Spring은 주력 경험으로 유지하되, 이 프로젝트를 나중에 Spring으로 재작성하는 것을 전제하지 않는다.
- 이 프로젝트의 포트폴리오 가치는 Memory, Context, Permission, 실패 복구를 설계하고 실사용으로 검증하는 데 있다.

## 3. 제품이 유지할 네 가지 정보

| 정보 | 예시 | 변화 원칙 |
| --- | --- | --- |
| 장기 기억 | 사용자는 Java 백엔드 개발을 준비한다 | 사용자 정정·만료 시 갱신 |
| 진행 중인 일 | ieum의 배포 기반을 만드는 중이다 | 완료·보류·재개 상태 유지 |
| 현재 맥락 | 기술 선택은 끝났고 구현은 아직 시작하지 않았다 | 관측한 사건과 마지막 확인 시각으로 갱신 |
| 비서의 정체성 | 모르는 것은 인정하고, 필요하면 반대 의견을 설명한다 | 버전 관리된 원칙과 확인된 피드백으로 조정 |

모든 정보를 ‘장기 기억’ 하나로 취급하지 않는다. ‘오늘은 짧게 답해줘’는 영구적인 선호가 아니다. 일정에 회의가 있다고 실제로 회의 중이라고 확정하지 않는다.

## 4. 자아·친밀함·개인화의 의미

구현할 정체성은 역할, 말투, 행동 원칙, 공유된 경험, 약속, 실수의 수정 이력이다. 주관적 경험이나 의식을 갖췄다고 주장하거나, 이를 구현 완료 조건으로 사용하지 않는다.

친구 같은 경험은 편안한 대화, 맥락의 연속성, 근거 있는 공감, 필요할 때의 이견 제시로 만든다. 실제 수행하지 않은 활동이나 확인할 수 없는 감정을 사실처럼 꾸미지 않는다. 사용하지 않은 기간에 죄책감을 유도하지 않는다.

사용자의 명시적 피드백으로 응답 방식을 조정한다. 반복 패턴은 가설로 취급하며, 사용자의 성격을 일방적으로 확정하지 않는다. 무응답은 반대나 관심 없음으로 단정하지 않는다.

**친밀도와 권한은 분리한다.** 오래 사용했다고 메일 전송이나 일정 생성 권한을 자동 확대하지 않는다.

## 5. 거의 실시간이라는 목표의 경계

초기에는 앱 대화와 사용자가 입력한 진행 상황만 관측한다. 이후 허용된 Calendar·메일 이벤트와 사용자가 시작한 음성 세션을 추가한다.

- 관측한 변화가 있을 때 현재 상태를 갱신한다.
- 모든 상태에 출처와 마지막 확인 시각을 둔다.
- 입력이 없는 동안 사용자의 행동을 알고 있다고 말하지 않는다.
- 상시 LLM 호출 대신 이벤트 저장 → 규칙 필터 → 필요한 판단 순서를 사용한다.
- 웹 앱이 닫혀 있어도 계속 마이크를 듣거나 OS 작업을 관측한다는 보장은 하지 않는다. Companion과 알림은 별도 단계다.

## 6. 첫 사용 범위

본인 한 명을 위한 모바일 웹으로 시작한다. 공개 가입·팀 기능·결제·음성·메일·일정은 첫 사용 범위에 없다.

첫 번째 대표 시나리오:

1. ‘이번 프로젝트는 Next.js와 Supabase로 만들기로 했어’를 명시적으로 저장한다.
2. 진행 중인 일에 ‘배포 기반 만들기’, 다음 행동에 ‘로그인 연결’을 기록한다.
3. 다음 날 새 대화에서 ‘어디부터 하면 되지?’라고 묻는다.
4. 마지막 결정과 미완료 작업을 근거로 다음 행동을 안내한다.
5. 사용자가 완료나 변경을 알려주면 이전 상태를 반복하지 않는다.

첫 버전은 자동 저장보다 명시적인 기억 등록으로 출처·정정·활용 흐름을 검증한다. 저장량이 작을 때는 제한된 활성 기억과 작업 상태를 전달하고, 검색 필요가 생기면 벡터 검색을 추가한다.

## 7. 설계 원칙

1. 과거 대화를 전부 Context에 넣지 않는다. 필요한 정보와 최근 대화만 제한된 분량으로 사용한다.
2. 모델은 교체 가능한 추론 엔진이다. 기억·상태·권한은 애플리케이션과 DB가 소유한다.
3. 사용자 직접 발화, 모델 추론, 외부 자료를 구분한다.
4. 저장된 사실에는 출처·시점·상태가 있어야 한다.
5. 정정·삭제는 검색과 요약에도 반영한다. 삭제된 내용이 재추출로 살아나지 않게 한다.
6. 모델이 제안한 실행을 서버가 검증한다. 기억이나 외부 자료가 정책을 변경할 수 없다.
7. 미래를 위한 큰 추상화보다 현재 작업의 명확한 경계를 만든다.
8. TypeScript는 학습하면서 사용하되 인증·기억·권한·비용 코드는 이해하고 넘어간다.
9. 작업 완료는 코드 작성이 아니라 동작 확인과 상태 기록까지다.

## 8. 성공을 판단할 지표

첫 지표는 목표값을 가정하기보다 고정 시나리오와 실제 사용 일지로 기록한다.

| 영역 | 관측할 것 |
| --- | --- |
| 연속성 | 이미 설명한 결정을 다시 설명해야 한 횟수 |
| 기억 품질 | 잘못된 개인 사실, 구버전 사실 사용, 근거 없는 단정 |
| 작업 추적 | 완료한 일을 다시 권하거나 다음 행동을 놓친 횟수 |
| 정정·삭제 | 사용자 수정 후 옛 정보가 다시 나타나는지 |
| 개인화 | 확인한 응답 선호가 적절한 상황에서 적용되는지 |
| 선제 제안 | 유용함·방해됨·중복 피드백 |
| 운영 | 응답 지연, 실패 작업, 일별 API 사용량 |

## 9. 문서 관리 규칙

새로운 사용자 지시가 이전 계획보다 우선한다. 변경 시 결정 기록과 현재 상태도 함께 갱신한다. 제안값을 사용자 확정으로 바꾸지 않는다. 기능 완료 상태에는 검증 근거를 기록한다.

이 문서는 제품 방향이며 실행 권한을 부여하는 문서는 아니다. 계정 연결·배포·쓰기 동작은 해당 작업의 실제 사용자 요청과 접근 권한을 따른다.
