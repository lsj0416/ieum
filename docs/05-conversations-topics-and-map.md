# ieum — S2 이후 대화·주제·지도 확장 지침

작성: 2026-09-16 · 버전: 제안 0.1 · 저장 위치: `docs/05-conversations-topics-and-map.md`

저장소에 편입하며 1절의 문서 정합성 지적을 반영했다. README와 04의 오래된 S0/S1 서술은 2026-09-16에 고쳤고, 이 문서의 단계 구분을 02의 백로그와 03의 결정(D40~D44)에 연결했다. 배포 URL은 현재 정상 동작한다.

이 문서는 현재 개발 에이전트에게 전달할 설계 및 작업 지침이다. 기존 S2 기능을 유지하면서 S3/S4 계획을 구체화한다. 문서 작성만 수행했으며 원격 파일, 코드, DB, 배포를 변경하지 않았다. 실제 작업 브랜치가 main보다 앞서 있다면 그 코드를 먼저 확인한다.

- README는 현재 단계를 S0로 표기하고, 인계 문서의 일부 항목은 앱 없음·Provider 미정·다음 작업 S1-02로 남아 있다. 최신 작업 기록과 모순된다. 구현 전 문서 정합성부터 복구한다.

## 2. 사용자 요구와 설계 제안 구분

### 사용자 요구

1. 사용자가 직접 주제를 정해 대화를 시작할 수 있다.
2. 평소 대화에서 반복되는 주제는 자동으로 발견하고 섹션으로 정리한다.
3. 임베딩과 주제 관계를 시각화해 대화가 어떤 영역에 모이는지 보고 싶다.
4. 대화창이 달라져도 하나의 비서와 맥락을 이어가야 한다.
5. 지금 S2를 기반으로 고도화한다. 전체 프로젝트를 재시작하지 않는다.

### 이번 문서의 기본 제안

- 기본 진입점은 마지막으로 선택한 대화를 이어가는 /chat이다. ‘기본 대화’를 별도 영구 대화 하나로 강제하지 않는다.
- Conversation은 원문 흐름, Topic은 여러 흐름의 관련 부분을 모으는 공간이다.
- Topic과 Work Item을 구분한다. Kafka라는 주제는 작업이 아니고, Kafka 면접 정리는 완료 가능한 작업이다.
- 주제 목록과 지도는 동일 Topic 데이터를 서로 다르게 보여준다.
- 자동 생성은 원문 이동·삭제·대화 전환을 유발하지 않는다. 분류 실패 시에도 채팅은 정상 동작한다.
- 지도 1차는 주제 관계도다. 고차원 임베딩을 2D로 투영한 대화 지도는 데이터와 평가 준비 후 추가한다.

자동 생성 기준 수치·UI 경로·DB 필드명은 구현 제안이지 사용자 확정값이 아니다. 기존 코드와 충돌하면 의도를 유지하는 최소 변경을 택하고 이유를 기록한다.

## 3. 핵심 개념과 관계

| 개념 | 의미 | 예시 |
| --- | --- | --- |
| Conversation | 시간순 원문 메시지 흐름 | 어제 나눈 일반 대화 |
| Segment | 특정 주제가 이어진 메시지 구간 | 그 대화 중 TypeScript를 논의한 5개 메시지 |
| Topic | 여러 Segment와 기억을 묶는 주제 | ieum 개발, TypeScript 학습 |
| Memory | 확인된 사실·선호·목표·사건 | 사용자는 Java가 더 익숙함 |
| Work Item | 진행·완료 상태가 있는 일 | ieum 대화 목록 구현 |
| Topic Relation | 근거가 있는 주제 사이 연결 | TypeScript 학습이 ieum 개발과 관련됨 |

관계 원칙:

- Conversation 1:N Message, Conversation 1:N Segment.
- Segment N:M Topic. 한 구간은 0개 또는 여러 주제에 연결 가능하다.
- Topic N:M Memory. 주제 연결은 기억의 사실성 확인과 별개다.
- Work Item은 기존 S3 설계를 사용하며 초기에는 대표 Topic 1개에 선택적으로 연결한다.
- Conversation의 선택 주제는 답변의 기본 범위를 돕는 값이다. 대화 전체가 항상 그 주제라고 분류하지 않는다.

원본 Message ID와 Conversation ID를 보존한다. 새 모델·분류 버전을 도입해도 원문이 이동하지 않게 한다.

## 4. UX 동작 계약

### 4.1 대화 목록과 새 대화

- /chat 접속 시 마지막 선택 대화가 유효하면 복원한다. 없으면 최근 대화, 전혀 없으면 빈 화면이다.
- 특정 대화 링크는 /chat/[conversationId] 또는 기존 라우팅에 맞는 동등한 주소로 표현한다.
- ‘새 대화’는 빈 화면으로 열고 첫 메시지 전송 시 DB 생성하는 방식을 기본 제안으로 한다. 빈 대화가 쌓이지 않게 한다.
- 사용자가 대화 이름을 바꾸면 자동 제목 생성이 덮어쓰지 않는다.
- 기존에 대화가 하나뿐인 사용자에게 그 대화를 그대로 노출한다. migration이 메시지를 새 대화로 옮기지 않는다.
- 생성 중 다른 대화로 이동하면 기존 요청은 원래 conversationId에만 결과를 저장한다. 화면이 바뀌었다고 새 창에 token을 붙이지 않는다. Abort/부분 저장 규칙은 기존 S1 구현을 유지한다.
- 목록의 ‘숨김/보관’과 실제 원문 삭제는 구분한다. 대화 삭제 기능이 아직 없다면 이번 변경에서 억지로 추가하지 않는다.

### 4.2 주제 섹션

모바일 기본 화면은 대화다. 주제 목록은 메뉴/보조 화면으로 열고, 지도는 주제 화면 안의 선택 보기로 둔다. 대화·기억함·주제의 기존 접근성을 유지한다.

Topic 상세에는 제목, 생성 방식(직접/자동), 짧은 요약, 마지막 관련 활동, 근거 대화, 연결 기억, 진행 중인 일, ‘이 주제로 대화’를 표시한다. 존재하지 않는 결정이나 다음 행동을 모델이 채워 넣지 않게 한다.

‘이 주제로 대화’는 해당 Topic에 대해 마지막으로 사용한 대화를 제안하되 새 대화 시작도 제공한다. 서로 다른 원문 대화를 이어 붙여 하나의 대화처럼 보이지 않게 한다.

다른 주제로 이야기가 바뀌어도 자동 창 이동이나 입력 중단을 하지 않는다. 나중에 관련 구간을 연결한다. 사용자가 현재 주제 범위를 해제하거나 변경할 수 있게 한다.

### 4.3 사용자가 고치는 방법

- 제목 변경: Topic ID는 유지한다.
- 잘못 연결됨: 해당 Segment와 Topic의 연결을 해제하고 자동 재연결 금지 override를 남긴다.
- 합치기: 대상 Topic ID로 연결을 옮기고 이전 ID는 redirect/alias로 남긴다. 사용자 승인으로만 수행한다.
- 나누기: 초기에는 새 Topic 생성 후 구간 선택·이동으로 제공한다. 고급 자동 분할은 보류한다.
- 숨기기: 탐색 화면에서 감춘다. 기록 삭제를 뜻하지 않는다.
- 자동 정리 중지: 후보 생성을 멈춘다. 기존 데이터 삭제는 별도다.

숨김과 ‘답변에서 사용하지 않기’를 같은 동작으로 구현하지 않는다. 두 옵션을 제공한다면 이름과 효과를 명확히 구분한다.

## 5. 자동 주제 발견

### 5.1 입력과 처리 단위

매 메시지마다 전체 이력을 분석하지 않는다. 완료된 새 턴을 커서 기반 배치로 읽고, 짧은 대화 구간을 구성한다. 사용자 발화를 증거의 중심으로 삼고 답변은 문맥 해석용으로만 사용한다. assistant가 나열한 기술 이름이나 긴 답변 분량을 사용자 관심 근거로 집계하지 않는다.

excluded_from_context 또는 사용자가 분석 제외한 원문은 후보 생성·요약·임베딩 입력에서 제외한다. S2의 ‘기억만 잊기’와 ‘출처 제외’ 의미를 코드에서 확인하고 그대로 연결한다.

### 5.2 처리 흐름

1. 미처리 구간을 읽고 기존 Topic 이름·alias와 비교한다.
2. 모델은 Topic 후보, 근거 Message ID, 연결 이유를 구조화해서 제안한다.
3. 서버는 사용자 범위·구간 소유권·Message ID·출처 제외 상태·필드 길이를 검증한다.
4. 같은 뜻의 기존 Topic과 연결하되 애매한 경우 별도 후보로 둔다.
5. 후보 생성과 Topic 활성화를 분리한다. 낮은 확신의 후보는 지도에 노출하지 않는다.
6. 새 후보/연결은 기록하되 답변 생성 지연에 포함하지 않는다.

초기 후보 활성화 기준 제안: 서로 다른 2개 이상의 대화 또는 2개 이상의 활동일에서 반복됐고, 서로 다른 근거 구간이 3개 이상이면 자동 섹션을 만들 수 있다. 숫자는 실사용 후 조정한다. 명시적으로 이름 붙인 프로젝트와 ‘이 주제로 관리해줘’ 요청은 수동 등록 경로로 즉시 활성화할 수 있다.

하나의 긴 오류 해결 대화를 여러 조각으로 나눠 임계치를 넘긴 것을 반복 관심으로 계산하지 않는다. 분류 confidence는 확률로 표시하지 않는다.

### 5.3 관심도와 주제 활동량

지도는 먼저 ‘대화·주제 지도’라고 부른다. 주제의 사용자 발화 수, 대화 구간 수, 활동일 수, 최근성, 사용자가 표시한 관심을 구분해 저장한다. ‘많이 언급함’만으로 선호나 전문성을 확정하지 않는다.

명시 관심 표시는 사용자만 변경한다. 민감한 건강·관계 정보는 기본 자동 공개 섹션 생성에서 제외하거나 별도 opt-in 대상으로 처리한다. 이는 타인 공개 여부뿐 아니라 휴대폰 첫 화면 노출을 고려한 규칙이다.

### 5.4 고정성과 비용

처음부터 임베딩을 필수로 하지 않는다. 기존 alias와 작은 Topic 후보 목록을 이용해 시작할 수 있다. 필요할 때 pgvector를 도입해 후보 검색 비용을 낮춘다. 생성 모델과 임베딩 모델은 별도로 관리한다.

동일 구간·내용 hash·분류 버전은 재처리하지 않는다. 사용자 수정/숨김 override를 모델 결과보다 우선한다. 일별 처리 개수·입력 토큰 상한과 전역 예산을 공유한다. API 실패 시 채팅과 기존 섹션은 계속 사용할 수 있어야 한다.

## 6. Context 적용 규칙

Topic을 선택했다고 관련 원문 전체를 프롬프트에 넣지 않는다.

현재 질문 + 최근 대화 + 관련된 확인 기억 + 선택 Topic의 유효 요약 + 연결된 작업의 마지막 결정/다음 행동을 예산 내에서 조합한다. 기존 S2 기억 예산과 합산해 상한을 지키고 중복 근거를 제거한다.

주제 선택은 우선순위 신호이지 검색 차단벽이 아니다. 사용자가 다른 주제를 명시하면 그 질문을 우선하고, 여러 작업 중 대상이 모호하면 확인한다. 자동 분류 때문에 인격·시스템 규칙·실행 권한을 바꾸지 않는다.

Topic 요약은 원문에서 파생된 비신뢰 데이터로 전달하고 시스템 정책으로 승격하지 않는다. 기존 인계에는 기억을 시스템 지시에 붙인다고 되어 있으므로 실제 Context 코드를 검토해 권한 있는 지시와 자료를 구분한다. 모델이 써준 요약을 다시 사용자 사실 근거로 순환 재학습하지 않는다.

Context trace에는 전달한 memory/topic/work ID와 버전을 기록한다. ‘전달한 정보’와 모델이 실제 인용한 정보를 구분한다.

## 7. 지도 설계

### 7.1 1차: Topic 관계도

같은 Topic 데이터로 목록/지도를 전환한다. 노드는 Topic, 선은 관계이며 최신 기간 필터를 두 방식에 동일 적용한다.

| 요소 | 표시 의미 |
| --- | --- |
| 노드 | 활성 주제 1개 |
| 크기 | 선택 기간의 서로 다른 근거 구간 수, 상한 적용 |
| 색 | 주제 종류 또는 주제 구분. 한 화면에서 의미를 혼합하지 않음 |
| 선 | 사용자 확인 관계 또는 함께 등장한 구간의 연결 |
| 클릭/탭 | 동일 Topic 상세와 근거 대화 |

처음에는 관계가 없는 노드를 억지로 연결하지 않는다. 지도에 나타난 가까움이 의미 유사도인지 단순 배치인지 안내한다. force layout을 쓴다면 그 좌표를 검색·관심도 계산에 재사용하지 않는다.

관계 타입은 co_occurs(함께 등장), semantic_similar(벡터 유사), supports(명시적 도움 관계)처럼 구분한다. supports 같은 의미 관계는 근거 또는 사용자 확인 없이는 자동 확정하지 않는다. 지도 1차는 co_occurs/수동 관계만으로도 충분하다.

모바일에서는 노드 수 상한·선택 강조·확대/축소·목록 보기·탭으로 상세 열기를 제공한다. hover 전용 조작을 만들지 않는다. 전체 네트워크를 처음부터 다 그리지 않고 상위 주제와 선택 주제 주변으로 제한한다.

### 7.2 2차: 임베딩 기반 대화 지도

점은 대화 구간, 영역 라벨은 Topic이다. 같은 임베딩 모델/버전의 벡터만 사용한다. Topic ID는 2D 좌표와 독립적이며 하나의 구간은 여러 주제에 연결될 수 있다.

군집과 검색은 원래 벡터 또는 평가된 중간 차원에서 처리한다. 화면용 2D 결과만으로 의미 관계·관심도·기억 검색을 결정하지 않는다. UMAP 등의 차원 축소는 정보 손실이 있으므로 위치는 탐색 보조다.

배치 갱신, 고정 seed, 기존 좌표에 새 점을 추가하는 전략 또는 좌표 정렬을 검토한다. seed 고정만으로 데이터 추가 시 배치가 유지된다고 보장하지 않는다. 레이아웃 버전을 저장하고 필터 변경마다 전체 지도를 새로 계산하지 않는다.

LLM은 대표 구간을 바탕으로 영역 이름을 제안한다. 사용자가 수정한 이름은 유지한다. 근거 없는 군집에도 그럴듯한 이름을 강제로 붙이지 않는다. 데이터가 적으면 빈 지도 대신 주제 목록과 안내를 사용한다.

2D 지도 라이브러리·군집 알고리즘·Worker 도입은 이 단계에서 평가한다. 이번 S3 변경에 새 Python 서비스·Graph DB를 필수로 추가하지 않는다.

## 8. 데이터 변경 제안

기존 migration 전체와 실제 DB를 먼저 확인한다. 과거 migration을 수정하지 말고 다음 번호에 additive migration을 작성한다. 아래는 개념 모델이며 바로 실행할 SQL이 아니다.

| 데이터 | 단계 | 주요 필드/제약 |
| --- | --- | --- |
| topics | S3-B | id, owner_id, title, kind, source(manual/auto), status(candidate/active/archived), hidden_at, version, last_activity_at |
| conversation의 선택 주제 | S3-B | optional topic_id. 분류의 진실이 아니라 대화 기본 범위 |
| conversation_segments | S3-B | id, conversation_id, start_message_id, end_message_id, source_version |
| topic_segments | S3-B | topic_id, segment_id, source, decision(include/exclude), 근거; pair unique |
| topic_memories | 필요 시 | topic_id, memory_id. 현재 활성 기억의 실제 상태를 재검증 |
| work_items와 topic 연결 | S3-B | 기존 S3 work_items 설계에 nullable topic_id |
| topic_aliases | S4-A | topic_id, normalized_alias; 자동 합치기보다 후보 조회 용도 |
| topic_summaries | S4-A | topic_id, content, source_revision, generated_at, status |
| summary_sources | S4-A | summary와 source segment/memory version 연결 |
| 분류 jobs/checkpoints | S4-A | source cursor/hash, extractor_version, 상태, lease, attempts, deletion_revision |
| topic_relations | S4-B | from/to, type, evidence, source, version |
| 지도 좌표 cache | 이후 | node_id, layout_version, x, y. 파생 데이터로 취급 |

RLS는 Topic과 연결 대상 양쪽의 소유권을 확인해야 한다. 본인 Topic에 타인의 Message/Memory를 연결하는 것도 거절한다. Segment 양끝 Message가 같은 Conversation에 속하고 올바른 순서인지 서버/DB에서 검증한다. 전역 seq의 범위를 읽을 때 반드시 conversation_id 조건을 함께 사용한다.

자동 처리용 secret client가 RLS를 우회한다면 같은 검증을 서버에서도 수행한다. 다중 REST 호출로 원자성을 가정하지 않는다. merge·override 변경·삭제 연쇄 등은 트랜잭션 또는 검증된 RPC로 묶는다.

## 9. 정정·삭제·동시 처리

이 기능에서 가장 중요한 회귀 위험은 삭제한 내용이 Topic 요약과 지도에서 다시 드러나는 것이다.

- 읽을 때 항상 현재 원문 제외 여부와 기억 상태를 확인한다. 오래된 연결 테이블만 믿지 않는다.
- 정정/출처 제외 시 관련 Topic summary를 즉시 invalid 상태로 만들어 노출·Context 전달을 중단한다. 재생성이 끝날 때까지 이전 요약을 계속 쓰지 않는다.
- 관련 벡터·지도 점·대표 발췌·근거 건수도 제거/재계산한다. 모든 근거가 사라진 주제는 빈 상태 또는 보관 처리한다.
- job은 시작 시 source/deletion revision을 읽고 commit 전 다시 비교한다. 오래된 결과가 삭제/사용자 override를 덮어쓰지 못하게 한다.
- 숨김은 삭제가 아니다. 원문 제외는 Topic 분석에도 적용되지만 기억만 잊기 정책과 혼동하지 않는다. 기존 사용자에게 보이는 의미를 변경한다면 명시적으로 설명하고 이관한다.
- 이전 assistant 응답과 새 요약이 삭제 내용을 복제했을 수 있다. 기존 S2 정책과 함께 검토하고 관련 Context를 보수적으로 제외하는 범위를 정한다.
- Topic 자동 등록이 성공해도 기억 저장·사실 확정·권한 승인이 자동으로 따라가지 않는다.

## 13. 여러 에이전트가 이미 작업 중인 경우

실제 작업자 명단과 브랜치를 모르는 상태이므로 이 문서가 업무를 자동 배정하지는 않는다. 담당자들이 다음 경계만 공유한다.

- 대화 탐색/UI 담당: Conversation ID 라우팅, 선택 상태, 스트리밍 전환 처리.
- 데이터/Context 담당: Topic/Segment 계약, 소유권·정정·삭제, 작업 Context.
- 자동화/지도 담당: 앞의 데이터 계약이 확정된 후 증분 분류와 파생 시각화.

migration 번호와 공통 DTO는 한 담당자가 조정한다. 서로 다른 브랜치에서 같은 migration 번호를 사용하거나 Context 예산을 각각 추가하지 않는다. 선행 PR이 안정되기 전에는 후속 기능 전체를 병합하지 않는다.
